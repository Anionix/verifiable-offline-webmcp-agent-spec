# 6つの運用品質判定の参照実装

<!-- machine-contract: PROPOSED -> EXECUTING -> VERIFIED_SYNTHETIC; synthetic evidence cannot authorize a measured-production claim. -->

## 何のためのものか

処理量、待ち時間、予測の確かさ、結果の確率、重大事故の確率を、都合のよい総合点でごまかさず判定する境界です。1つでも条件を満たさなければ`STOP`になります。

```text
入力
  ↓
来歴と要約値を確認 ── 不一致 ──> STOP
  ↓
6つの判定を全部実行 ── 1つでも不成立 ──> STOP
  ↓
PASS
  └─ 模擬値なら「判定処理を確認した」だけ。本番品質は未計測のまま。
```

現在公開している入力は、結果を何度でも再現できる模擬値です。本番環境の可用性、遅延、予測精度、誤処理率、二重実行率を測ったものではありません。

## 6つの判定

| 検証番号 | 確認すること | 不成立時 |
|---|---|---|
| `TEST-SLO-001` | 平均処理率が平均流入率より厳密に大きい | `STOP` |
| `TEST-SLO-002` | 平均待ち件数、流入率、平均待ち時間が整合する | `STOP` |
| `TEST-SLO-003` | 検証用データによる確率校正が上限内 | `STOP` |
| `TEST-SLO-004` | 4種類の結果確率が非負で、合計がちょうど1 | `STOP` |
| `TEST-SLO-005` | 誤処理と二重実行の確率上限を両方守る | `STOP` |
| `TEST-SLO-006` | 模擬値と実測値を混ぜず、来歴と要約値が一致する | `STOP` |

### 1. 処理能力

平均流入率を (\lambda)、平均処理率を (\mu) とすると、合格条件は次です。

\[
\mu > \lambda
\]

実装では丸め誤差を避けるため、小数へ変換せず次を整数のまま比較します。

\[
処理完了数 \times 観測時間 > 流入数 \times 処理稼働時間
\]

等しい場合も余裕がないため停止します。観測時間と処理稼働時間は別項目にし、単位の取り違えを防ぎます。

### 2. 待ち行列の整合性

[Littleの原論文](https://pubsonline.informs.org/doi/10.1287/opre.9.3.383)の関係 (L=\lambda W) を、同じ観測窓の全流入を含む待ち時間標本で確認します。

\[
待ち件数の時間積分 \times 待ち時間標本数
= 流入数 \times 待ち時間合計
\]

許容誤差は100万分率で指定します。標本が流入全件を含まない場合は、数値が偶然一致しても停止します。

### 3. 予測確率の校正

モデルが自分で申告した「自信」は判定に使いません。[Guoほかの校正研究](https://arxiv.org/abs/1706.04599)を根拠に、学習用とは分けた検証用データについて次を計算します。

- 予測確率帯ごとの予測値と実際の割合の差
- 予測確率と正解値の二乗誤差

入力に自己申告の自信値が入っていても証拠として保持するだけで、値を変えても判定結果は変わりません。[Chowの棄却判断の原論文](https://research.ibm.com/publications/on-optimum-recognition-error-and-reject-tradeoff)も、誤りと判断保留を分ける設計根拠として参照します。

### 4. 結果確率の保存

4種類の結果確率 (q_T, q_B, q_R, q_H) はすべて0以上で、100万分率の合計が厳密に1,000,000でなければなりません。

\[
q_T+q_B+q_R+q_H=1{,}000{,}000
\]

負数、合計不足、合計超過はすべて停止します。

### 5. 誤処理と二重実行の上限

誤処理確率と二重実行確率は、総合点から差し引く罰点ではなく、越えてはいけない上限です。[Altmanの制約付き意思決定過程](https://www-sop.inria.fr/members/Eitan.Altman/PAPERS/h.pdf)を設計根拠にしています。

確率を分数 (n/d)、上限を10億分率 (b) とすると、合格条件は次です。

\[
n \times 1{,}000{,}000{,}000 \leq b \times d
\]

表示値は切り捨てることがあるため、判定自体は必ず元の分数で行います。総合点がどれだけ高くても、この上限を越えれば停止します。

実測値を使う場合は、点推定ではなく片側上限であることと、95パーセント以上の信頼水準を明記しなければ停止します。現在の公開例は正確な模擬分数であり、実測上限ではありません。

### 6. 模擬値と実測値の分離

4つの入力区分には、それぞれ次を結び付けます。

- 情報を追うためのUUIDバージョン5
- 観測時刻を含むUUIDバージョン7
- 観測時刻
- `SYNTHETIC`または`MEASURED`
- 入力内容のSHA-256要約値
- 実測時だけ測定環境

1回の判断で模擬値と実測値が混ざる、識別子と時刻が合わない、証拠の観測時刻が評価時刻より未来、要約値が合わない、実測環境がない、という場合は停止します。未来にしか存在しない証拠を、現在の判断へ使うことはできません。

## 反例も必ず試す

自動試験は、合格例だけでなく次の不合格例を固定しています。

- 処理率が流入率以下
- 待ち行列の式が不一致、または待ち時間標本が不足
- 学習用データ、校正不良、自己申告値の改変
- 負の結果確率、または合計が1ではない
- 高い総合点を付けても誤処理・二重実行の上限超過
- 実測値なのに片側上限ではない
- 模擬値と実測値の混在、誤表示、要約値不一致、整数でない入力、評価時刻より未来の証拠

## 再現方法

```bash
make evidence-slo
make validate
```

`make evidence-slo`は明示的に証拠ファイルを更新します。`make validate`は追跡ファイルを書き換えず、TypeScript試験に加えてPythonから公開証拠の識別子、時刻、6件の結果、模擬・実測分離、実測件数0を独立確認します。

現在確認できるのは、模擬入力に対する6つの判定と反例が再現可能であることです。実運用の標本、測定環境、可用性、遅延、予測校正、誤処理確率、二重実行確率は`UNMEASURED`です。
